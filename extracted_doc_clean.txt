1. Resumo executivo
O protótipo atual está fortemente alinhado ao EnergyMatrix no nível visual e conceitual. Ele já apresenta
dashboard, máquinas, estados, alertas, economia, relatórios e administração. O principal déficit é a ausência, no
ZIP original, de backend/API, persistência, motor analítico executável e um Competition Mode determinístico.
A primeira implementação deve transformar a interface em um sistema demonstrável sem tentar construir um
EMS industrial completo. A prioridade é provar um fluxo de ponta a ponta com dados simulados — agora sobre
uma fundação arquitetural sólida, de modo que as funcionalidades existentes evoluam sem reconstrução
estrutural.
Regra: qualquer funcionalidade média/alta que não seja necessária para a demonstração deve permanecer fora da
implementação da competição. A consolidação arquitetural não autoriza criar módulos de produto, telas, machine
learning, manutenção preditiva, controle industrial ou hardware real.

4. Arquitetura
4.1 Visão geral — monólito modular em camadas
React + TypeScript + Vite
        ↓  REST / HTTP
Node.js + TypeScript + Express
        ↓
Routes → Controllers → Application Services
                            ↓
                  Domain  +  Analytics
                            ↓
                 Ports (interfaces de repository)
                            ↑ implementados por
            Database (repositories PostgreSQL) → PostgreSQL
Simulator → Contrato de telemetria → Ingestion → Application
O frontend nunca acessa o banco: React → HTTP → Express → Controller → Service → Repository → PostgreSQL. A
arquitetura é um monólito modular; microsserviços, Kafka e Kubernetes estão fora de escopo. A arquitetura
industrial futura pode ser documentada, mas não deve bloquear a competição.
4.2 Separação em camadas
Presentation (routes, controllers, middleware, schemas, dto) · Application (services) · Domain (entidades, erros,
ports) + Analytics · Infrastructure (logger, relógio, fontes de telemetria) · Persistence (database) · Configuration ·
Shared (types, utils).

7.2 Esquema PostgreSQL
Dois grupos de dados: transacionais (tenants, plants, sectors, machines, alerts, interventions, tariffs, scenarios)
e temporais (telemetry, machine_states), estes últimos desenhados para otimização posterior como séries
temporais. Todas as tabelas têm chave primária, timestamps (created_at/updated_at), foreign keys e
constraints. Status e qualidade usam CHECK com texto (não ENUM nativo), por serem mais fáceis de migrar.
Valores monetários em numeric; telemetria em double precision.

7.3 Telemetria de alto volume
•Estrutura pensada para grandes volumes, consultas por máquina, por intervalo, agregações, séries temporais
e retenção futura. A PK (machine_id, ts) cobre consultas por máquina + intervalo; um índice adicional em
ts só entra se houver consultas entre máquinas.
•A telemetria não repete tenant_id: obtém-se pela máquina, evitando custo de armazenamento. Se a leitura
por tenant virar gargalo, isso pode ser revisto.
•Preparação para TimescaleDB sem dependência rígida: hypertable, compressão, retenção e agregados
contínuos entram como migrations futuras; o projeto funciona sem a extensão.
7.4 Migrations
O banco é criado exclusivamente por migrations versionadas (ferramenta sugerida: node-pg-migrate,
migrations em SQL). Nunca depender de criação manual de tabelas. A numeração reflete a ordem real:
001_initial_schema        (tenants, plants, sectors)
002_machines
003_telemetry
004_machine_states
005_alerts                (alerts + alert_events)
006_tariffs
007_interventions
008_scenarios
009_audit_logs
010+ reservadas: users/roles, sensors/gateways (quando houver consumidor)
7.5 Seeds
Separados das migrations; reproduzíveis, previsíveis e idempotentes (ON CONFLICT). Sem dados aleatórios.
Conteúdo mínimo: tenant/planta/setor de demonstração, as 3 máquinas com os parâmetros da seção 14 e tarifa
padrão configurável (valor definido no seed e apresentado como estimativa).
7.6 Multi-tenancy e auditoria
A prioridade é estrutural: Tenant → Plant → Sector → Machine → Telemetry. As tabelas transacionais carregam
tenant_id. Não se implementa isolamento incompleto apenas para “constar” multi-tenancy. A tabela
audit_logs fica pronta para registrar actor, action, entity, entity_id, timestamp e metadata.

Configuração

TransaçõesBEGIN → operação A → B → C → COMMIT; em erro, ROLLBACK. Operações cuja integridade dependa
do conjunto (ingestão + alertas; ativar/resetar cenário) não podem ficar parcialmente concluídas.
ErrosPadrão único: { "error": { "code": "MACHINE_NOT_FOUND", "message": "..." } }.
Classes AppError, ValidationError, NotFoundError, ConflictError, DatabaseError e middleware central
errorHandler.
Logging
Níveis INFO, WARN, ERROR, DEBUG. Campos: timestamp, service, operation, requestId, status, error.
Nunca registrar senhas, tokens, secrets ou dados sensíveis desnecessários.
HealthGET /api/health, /api/health/live (processo de pé), /api/health/ready (banco acessível

Graceful shutdownSIGTERM → bloquear novas requisições → aguardar as atuais → fechar pool → fechar recursos →

Middlewares

Validação

Paginação

Segurança
(preparação)
Espaço estrutural para authentication, authorization, RBAC, tenant isolation, audit logs e rate limiting
— sem implementar complexidade por antecipação, mas sem impedi-los.
PerformancePool, índices, paginação, consultas por intervalo, agregações, limites de retorno e processamento de
telemetria em loop interno controlado, sem bloquear requests HTTP. Sem otimização prematura.
Estrutura da API
app.ts (inicialização), server.ts (startup), routes.ts (registro) — facilita testes, bootstrap e

23. Critério de conclusão
23.1 Funcional
A versão está pronta quando o avaliador consegue executar a demonstração sem editar código e observar: 3
máquinas; dashboard; IDLE gerando desperdício e R$; anomalia explicável; alerta térmico; intervenção; recovery;
comparação antes/depois; reset; repetibilidade.
23.2 Arquitetural
A implementação não está concluída apenas porque o servidor inicia ou o banco possui tabelas. Ela só está
consolidada quando:
•cada camada possui responsabilidade definida e as dependências estão controladas;
•o banco possui migrations e os repositories isolam a persistência;
•services concentram a orquestração e analytics estão desacoplados de HTTP;
•configuração e tratamento de erros estão centralizados;
•health checks funcionam;
•frontend e simulador continuam funcionais;
•os testes existentes continuam passando.
Conclusão: o EnergyMatrix deve ser apresentado nesta etapa como um protótipo funcional de decisão energética,
não como um EMS industrial já implantado. O diferencial técnico da demonstração é o fechamento do ciclo: medir →
entender → monetizar → agir → comprovar. A fundação arquitetural desta versão permite sustentar essas
funcionalidades — e a evolução para medidores reais, MQTT e TimescaleDB — sem nova reescrita do núcleo.
